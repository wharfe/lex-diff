# 設計案 B（design-codex.md）への批評 — R1

担当: fresh Claude #3（親セッションの文脈を持たない独立セッション）

## finding 1 — critical: 「現在の条文」の隣に置く解説が、その条文の説明になっていない（162 件中 30 件）

**指摘**: 設計 B は「現在の条文」だけを鮮度管理し、同じページに並べる `plain_summary` /
`change_description` は出荷済み diff の annotation をそのまま持ってくる。`validate_articles`（§2-5）には
両者を突き合わせる規則が 1 つも無い。結果、今日の条文と、その上に「この条文は何をする条文か」として
出る文が食い違うページが量産される。

**根拠**（実測。各法令を `asof=2026-09-22` で取得し、
`lawtext.walk_tags(tree,{"Article"},stop_at={"SupplProvision"})` + `diff.format_paragraph` で
今日の本文を作り、設計 B が `plain_summary` の出所と定めた「施行日が最新の change」の
`paragraphs_after` と比較）:

```
articles compared: 162   text differs from diff's paragraphs_after: 30
```

代表例:

- **著作権法 第122条の2**（出所: `345AC0000000048_2025-05-31_2025-06-01.json`）
  - shipped `plain_summary`: 「裁判で「秘密保持命令」に違反した人に対する刑罰を定める条文」
  - 今日の第122条の2 本文: 「次の各号のいずれかに該当する場合には、当該違反行為をした者は、
    三十万円以下の罰金に処する。一　第百四条の二十七又は第百四条の四十の規定に違反して帳簿を備えず…」
  - → **番号が別の規定に付け替わっている。**「現在の条文」ブロックは帳簿義務違反の罰則を表示し、
    その直下に「秘密保持命令違反の刑罰を定める条文」と書く。読者に対する端的な虚偽。
- **刑法 第183条**（`140AC0000000045_2023-07-12_2023-07-13.json`）
  - shipped `change_description`: 「…**3年以下の懲役**または30万円以下の罰金に処するという、
    既存の犯罪類型を定めたものです。」（現在形）
  - 今日の第183条本文: 「…三年以下の**拘禁刑**又は三十万円以下の罰金に処する。」
  - → CLAUDE.md / brief §6-3 が「事故」として記録している**まさにその形**を、同じ法令で再生産する。
    刑法 181、道交法 117_3_2・118 も同型（懲役→拘禁刑）。
- **育児介護休業法 第29条**: `change_description` は「第二十一条第二項・第三項が追加された」と
  説明するが、今日の本文はその後の改正で更に変わっている。

設計 B は §2-4 で「古い改正の `plain_summary` は現在の条文の説明ではない」と正しく認識しながら、
対策を「**最新の** change から取る」で止めている。最新の change も古くなりうる
（著作権法 122_2 は 2025-06-01 の diff が最新、今日の版は 2026-06-24 施行）という事実が抜けている。

**処方**:
1. `build_law_articles` で、最新 change の `paragraphs_after` を正規化して今日の条文本文と比較する。
   **不一致なら `plain_summary` をページに出さない**（ブロックごと省く）か、見出しを
   「◯年◯月◯日改正時点でのこの条文の説明」に変えて時点付きの主張にする。
   この判定は `validate_articles` にも入れて、緑でないと保存しない。
2. `change_description` は履歴カードの中なので時点付きだが、現在形の断定が混じる。最低限、
   `law_summary.py` の廃止刑名禁止リスト（懲役/禁錮/禁固/禁こ）を、
   **今日の本文に当該語が無いのにテキストに出ている**場合だけ赤にする形で流用する。
3. brief §3 の表は `plain_summary` を無条件に「既存資産の組み替え」と書いているが、
   実データ上それは成り立たない。ここは brief 側の訂正も要る。

## finding 2 — critical: `753:754` の annotation を 753 に配ると、753 のページが 754 の中身を語る

**根拠**（`frontend/public/data/129AC0000000089_2026-03-31_2026-04-01.json`）:

| article_num | type | plain_summary |
|---|---|---|
| `753` | deleted | かつて『未成年者が結婚すると成年として扱われる』という成年擬制のルールを定めていた条文の欠番 |
| `754` | deleted | 夫婦が結婚している間に交わした約束（契約）を、あとから一方的に取り消すことができるというルール |
| `753:754` | added | **夫婦の間で結んだ契約を婚姻中はいつでも取り消せるとする「夫婦間契約取消権」に関するルール** |

`753:754` の本文は「削除」の 2 文字なのに、その `plain_summary` は 754 の内容を現在形で述べている
（annotation 生成時の既存の誤り）。設計 B の並べ替え規則「`enforcement_date` 降順、同日は
`entry_article_num` 昇順」では、同日 2 件の順序は `"753:754" < "754"`（文字列比較）なので
`753:754` が先頭に来る。§2-4 の「`plain_summary` は施行日が最新の change の annotation から取る」を
素直に実装すると、**第753条・第754条の両ページが「夫婦間契約取消権に関するルール」を掲げる**。
753 は成年擬制の欠番なので誤り。

**処方**: 展開時に配るのは `change_description` と diff 行だけにし、`plain_summary` は
**展開元エントリからは絶対に取らない**。展開元が持ち込む `cross_references` の自己参照
（`753:754` の refs に `754` が入っている＝754 のページが自分自身へリンクする）も除去規則が要る。

## finding 3 — high: 鮮度検証の本体テストが、実データで初日から赤になる

**指摘**: §4-2 の旗艦テスト `test_shipped_article_text_is_not_older_than_known_enforcement` は
「timeline の施行日のうち `asof` 以下で最大のもの > `source.amendment_enforcement_date` なら赤」。
設計 B は「古い timeline は判定を緩めるだけ」と書いているが、**2 つのエンドポイントが返す施行日は
同じ軸ではない**ので、今日の出荷 timeline と今日の API 応答で既に 11 法令中 2 法令が赤になる。

**根拠**（実測。左=出荷済み timeline の `enforcement_date` 最大値 ≤ 2026-09-22、
右=`law_data?asof=2026-09-22` の `revision_info.amendment_enforcement_date`）:

```
140AC0000000045 刑法         timeline 2026-05-22  /  law_data 2026-05-21   → RED
425AC0000000027 マイナンバー法 timeline 2026-08-22  /  law_data 2026-07-17   → RED
（他 9 法令は green）
```

- 刑法: timeline は `140AC0000000045_20260522_507AC0000000039`、law_data は
  `140AC0000000045_20260521_507AC0000000039` を返す（同じ改正法で施行日行が 1 日ずれている）。
- マイナンバー法: `law_revisions` は施行日 2026-08-22 の版を持つが、`law_data?asof=2026-08-23` も
  `asof=2026-09-22` も `..._20260717_508AC0000000056`（2026-07-17）を返す（asof を変えて 2 回確認）。

このテストは「articles が古い」ではなく「2 つのエンドポイントの不一致」で赤になる。実装時に赤を見た
人間がまずやるのは比較を緩めることで、そうすると受け入れ基準 4 は空になる。設計 B は §9 弱点 1 で
「甘すぎる」方向だけを自己申告しているが、実際には**まず厳しすぎる方向で壊れる**。

**処方**: 比較軸を `amendment_enforcement_date` ではなく `law_revision_id` 集合にする、あるいは
timeline 由来の下限を「`law_revisions` が知っているが `law_data` は返さない版」を許容する形にする。
少なくとも、**設計を採用する前にこの比較を実データで 1 回走らせて緑であることを示す**こと。

## finding 4 — high: `--all` が健全な repo で非ゼロ終了する（受け入れコマンドが赤）

**指摘**: §2-1 の glob は **12 法令**を返す（労働基準法 `322AC0000000049` を含む）。労基法は本則の改正が
0 件なので `articles` が空になり、§2-5 の規則 2「`articles` が空でない」で失敗する。§2-1 は
「最後に失敗した law_id を並べて非ゼロ終了」と定めているので、**§8 の受け入れコマンド
`uv run python scripts/articles.py --all` は何も壊れていない状態で毎回赤**になる。

**根拠**: `frontend/public/data/322AC0000000049_*.json` の本則エントリ数 = 0（実測）。
出荷 diff ファイルは 16 本・法令は 12、本則を持つ法令は 11（実測）。

**処方**: 「本則条文 0 件」を成功扱いにして**ファイルを書かない**ことを §2-1/§2-5 に明記する。

## finding 5 — medium: `data/articles/` が `.gitignore` に無い（設計の記述が事実と違う）

**根拠**（`.gitignore` 実物）:
```
data/raw/
data/diffs/
data/timelines/
data/proposers/
```
列挙式なので `data/articles/` は追跡対象になる。CLAUDE.md の
「`data/` Generated data (not committed — all subdirs gitignored)」という記述も、
この設計を入れた時点で偽になる。

**処方**: `.gitignore` に `data/articles/` を足すことを §2-1「変更: なし」に加える。
CLAUDE.md の当該行も直す対象に入れる。

## finding 6 — medium: `test_shipped_article_source_is_one_run` は構造上絶対に赤にならない

**指摘**: このテストは `source.asof` と `source.fetched_at` の日付一致を見る。ところが生成器は
`today` という 1 つの変数から `asof` を作り、同じ実行で `fetched_at` を打つので、
両者が食い違う経路が存在しない。検査しているのは「生成器が自分の書いた値を自分で写したか」であって、
brief §6-1 の根っこには触れていない。

**処方**: 形式検査として残してよいが、「§8-4 に対応」という位置づけを下ろす。
受け入れ基準 4 を実質的に担保しているのは finding 3 のテスト 1 本だけで、それが壊れている、と明記させる。

## finding 7 — medium: 180 日の時限装置は、この repo の唯一の壁時計依存テストになり、CI では直せない

**指摘**: 現行 108 テストは 0.87 秒で全部決定的（実測: `uv run pytest -q` → `108 passed in 0.87s`）。
この 1 本だけが「今日の日付」で結果が変わる。個人 OSS で、無関係な PR が突然赤になり、
**赤の直し方が「e-Gov へ 11 リクエストを投げて再生成し commit する」**である。CI はネットワークに
出ない方針なので CI 内では直せない。

さらに設計 B 自身が「ページ本文に『2026年9月22日時点』と明示するので期限切れでも嘘にはならない」と
書いている。**嘘にならないのなら CI を赤にする理由が無い**（この 2 文は互いを打ち消している）。

**処方**: CI から外し、`--verify` 相当か週次ジョブに移す。

## finding 8 — medium: `resolve_current` の範囲畳み込みが広すぎ、「条文が消えた」を静かに飲み込む

**根拠**（実測、`asof=2026-09-22` の本則 Article Num）:
```
129AC0000000089 民法         範囲ノード 8 個  例: 170:174, 367:368, 516:517, 534:535, 638:640
140AC0000000045 刑法         範囲ノード 3 個  例: 83:86, 73:76, 90:91
403AC0000000076 育児介護休業法 範囲ノード 1 個: 36:52   ← 17 条ぶんを 1 ノードが覆う
```
育児介護休業法は出荷対象 20 条文を持つ法令で、`36:52` が第36条〜第52条を覆う。将来この法令の第40条あたりが
対象に入り、かつ本文から消えたとき、設計 B の規則は `LookupError`（＝設計の核）に**到達せず**、
「本文=削除」の merged ページを静かに出荷する。

今日のデータでは ABSENT=0（11 法令すべて present か `753:754` merged で解決）は実測で確認した。
つまり今は当たらないが、規則そのものが緩い。

**処方**: merged と判定する条件を「範囲ノードの本文が実質『削除』相当」に限定する。
範囲が広いノードに落ちたときは `status: "merged"` ではなく、範囲幅と該当条番号を出して `LookupError` にする。

## この設計の最も弱い一点

**「現在の条文」だけ鮮度を守り、そのすぐ上に置く「この条文は何をする条文か」の鮮度を
誰も守っていないこと（finding 1）。**

設計 B は brief §6-1 の教訓を条文本文については完璧に移植した。しかし同じページに並ぶ解説文は、
出荷済み diff から無検査で持ってくる。実測で 162 条文中 30 条文が今日の本文と食い違い、その中には
**番号が別の規定に付け替わった著作権法122条の2**（本文は帳簿義務の罰則、解説は秘密保持命令違反の刑罰）と、
**CLAUDE.md が事故として記録している懲役→拘禁刑の再現**（刑法183ほか）が含まれる。
`validate_articles` の 7 規則はすべて「空でないか・形が合うか」であり、本文と解説の対応を見る規則が
1 つも無いので、この誤りは緑のまま 163 ページ全部に出荷される。ページの主役が条文本文であるぶん、
鮮度の外れた解説は「古い」ではなく「別の条文の説明」として読まれる。
