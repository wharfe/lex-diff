# 条文ページ（issue #4）— Gate 1 brief

lex-diff に「条文1本ごとのページ」を新設する設計を決める。
この brief と repo だけが、起草者・批評者・裁定者の共通の前提。

## 1. 背景（実測）

GSC 実測（lexdiff.com、2026-08-25〜2026-09-21 の4週）:

| ページ | imp | click | 平均順位 |
|---|---|---|---|
| `/diff/129AC0000000089_2026-03-31_2026-04-01`（民法） | 358 | **0** | 7.9 |
| `/law/416AC0000000123`（不動産登記法） | 91 | 3 | 6.4 |
| `/diff/416AC0000000123_2024-03-31_2024-04-01` | 57 | **0** | 6.9 |

`/diff` 配下はサイト最大の表示回数を持ちながらクリックが 0。順位は `/law` より上。

仮説: 流入が「条文そのものを読みたい」意図で、`/diff` は差分しか出さないため
スニペットの時点で用が無いと判断されている。

**この仮説の根拠は弱い。** page×query で分解しても、約 500 imp のうちクエリ名が
見えるのは 4 件だけ（GSC が少数クエリを匿名化する）。見えている 4 件は全部
「e-gov 民法 第754条 夫婦間の契約の取消権」「e-gov 民法 770条 離婚 2026」型で
仮説と一致するが、n=4 である。残り 99% の意図は不明。
**この薄さは設計の前提として明示的に扱うこと。**

## 2. 目的（goals）

1. 「○○法 第△条」で来た人が、その条文のページに着地して用が足りる状態を作る。
2. e-Gov が持っていない付加価値を同じページに載せる:
   その条文が **いつ・どう変わったか**、**何をする条文か**、**関連する条文**。
3. 既存の出荷済みデータを最大限使い、新しい LLM 生成を増やさない。

## 3. 作るもの（決定済み。ユーザー承認済み）

- URL: `/law/<lawId>/article/<条番号>`
- 対象: **その法令で実際に改正された本則の条文のみ**。全12法令で **164 ページ**
  （ユニーク条文数。内訳: 民法39 / 情プラ法23 / 育児介護休業法20 / 著作権法18 /
  建築基準法14 / 道路交通法14 / 消費者契約法12 / 刑法11 / 不動産登記法6 /
  マイナンバー法6 / 個人情報保護法1。労働基準法は本則の改正が無く 0）
- ページの構成ブロックと、その出所:

| ブロック | 出所 |
|---|---|
| 条文の見出し・章節パス | 既存 diff JSON（`title_after` / `section_path`） |
| **現在の条文（全文）** | **生成時に e-Gov から取得**（唯一の新規取得） |
| この条文は何をする条文か | 既存 `annotation.plain_summary` |
| この条文の改正履歴（年＋何が変わったか） | 既存 diff JSON（`annotation.change_description`）＋ `/diff` へのリンク |
| 関連する条文 | 既存 `annotation.cross_references` |

- 出荷済みエントリ 165 件すべてに `annotation` が付いている（実測）。
  解説の欠けるページは発生しない。
- 一括投入（段階投入はしない）。

## 4. 非目標（non-goals）

- 法令の全条文をページ化しない（民法だけで1050ページ。大半が e-Gov のコピーになり、
  薄いページの量産になる）。
- 附則（施行期日・経過措置）のページは作らない。既存の「本則だけ数える」規則と揃える。
- `/diff` を消さない・統合しない。単位が違う（改正まるごと ↔ 条文1本）。相互リンクする。
- 新しい LLM 生成を足さない。既存 annotation を組み替えるだけ。

## 5. 制約（constraints）

- **現在の条文の鮮度**。手元の `paragraphs_after` は「その改正の直後の条文」であって
  「現在の条文」ではない（民法第306条は 2024 版と 2026 版の2つが手元にある）。
  条文ページは中身の大半が条文全文なので、鮮度を外すとページの主張そのものが誤りになる。
  → 生成と同じ実行のなかで e-Gov から取得し、失敗したら raise、
     JST の日付が生成中に変わったら保存しない。`law_summary.py` が採用済みの形。
- 静的サイト生成（SSG）。`frontend/public/data/` に置いたものが出荷される。
- Python パイプライン（uv）＋ Next.js App Router。TypeScript strict。
- コード内コメントは英語、利用者向けテキストは日本語。
- 手書きコピーは検証器が見ない（`frontend/lib/law-seo.ts` の教訓）。
  ページのテンプレート文言に法的主張を書くなら、条件を落とさないこと。

## 6. 既知の文脈（この repo が既に踏んだ事故）

1. **鮮度をディスク上のファイルから判定しようとして2回失敗した。**
   ① `<law_id>_revisions.json` と突き合わせた → その第二のファイルの鮮度を
      誰も保証していない（`timeline.py` は既存ファイルを無期限に再利用する）。
      無い・壊れているときに素通りした。
   ② 最新 asof が今日の日付かを見た → asof は「いつの法令か」であって
      「いつ取得したか」ではない。`129AC0000000089_2026-04-01.json` は
      2026-03-26 に書かれていた。
   実害: 12法令中10法令が最新施行版より古い条文から要約され、刑法の全スナップショットが
   2025-06-01 の拘禁刑への統合より前だった。
   **根っこ: ディスク上のファイルは「いつ取得したか」を記録していない。**
2. 改正法の附則が本則の条文を上書きしていた（`suppl_key` で名前空間を分けて修正）。
   附則は手続きだけではない（労基法附則第138条は改正の実体そのものだった）。
3. 刑法の解説が廃止済みの刑名「懲役」を現行制度として説明していた。
4. 手書きの SEO 文言で「怠ると過料」と条件を落としかけた
   （正しくは「正当な理由がないのに怠ったときは十万円以下の過料」）。

## 7. この機能を既に持っている仕組みを探したか

**探した。以下は再実装しない。**

- `scripts/fetch.py::fetch_law_data(law_id, asof)` — e-Gov から法令全文を取得する。
  **新しい取得器は書かない。**
- `scripts/lawtext.py::walk_tags(node, tags, stop_at)` — 木から `Article` ノードを
  document 順で全部返す。`extract_text(node)` — ノードから平文を取る。
  **新しい木の走査は書かない。**
- `scripts/law_summary.py::fetch_evidence` / `main()` — 「同じ実行で取得する・失敗したら
  raise する・JST の今日を使う・生成中に日付が変わったら保存しない」の実装済みの形。
  **この4点は移植であって発明ではない。**
- `scripts/llm.py` — 今回は LLM を呼ばないので不要。
- Next.js App Router の `generateStaticParams` / `generateMetadata` — 既存の
  `/diff/[diffId]` と `/law/[lawId]` が同じ形で実装済み。`frontend/lib/data.ts` が
  `public/data/` から読む唯一の場所。**新しいデータ読み出し層は作らない。**
- 検討して**不採用**にしたもの: 条文の現行テキストを `data/raw` の既存スナップショットから
  読む案 — §6-1 の事故そのもの。

未検証の可能性として残るもの（批評で潰してほしい）:
- e-Gov API に「条文単位」の取得エンドポイントがあるなら、法令全文を取ってから
  抜き出す必要はないかもしれない。確認していない。

## 8. 受け入れ基準（acceptance criteria）

出荷時点で機械判定できるもの:

1. `uv run pytest` が緑。
2. 生成スクリプトが、取得に失敗したときに非ゼロで終了し、何も保存しないこと
   （テストで赤→緑を示す）。
3. 生成物の全ページに「現在の条文」が入っていること。空文字のページが0件。
4. 生成物のどのページにも、その法令の最新施行版より古い条文が入っていないこと
   （= 取得日が生成物に記録され、それが検証できること）。
5. `cd frontend && npm run build` が通り、164 ページが静的生成されること。
6. `npm run lint` が緑。

時間のかかる判定（出荷条件ではない）:

7. 8週後に GSC で `/law/*/article/*` の表示回数とクリックを見る。

## 9. 未決の論点（debate で攻めてほしい点）

1. **仮説の薄さ（n=4）に対して、164ページを一括で作るのは妥当か。**
   より安く仮説を検証する手があるなら、それを出すこと。
2. **「現在の条文」をどう生成物に記録し、どう検証するか。** 受け入れ基準4を
   満たす具体的な形（取得日をどこに持つか、テストがそれをどう読むか）。
3. **1条文が複数の改正で変わっている場合の1ページ内の構成。**
   実データでは道路交通法 `117_2_2` の1本だけ（2024-11-01 と 2026-04-01）。§10-1 参照。
4. **`/diff` と条文ページで同じ条文テキストが出ることの扱い。**
   canonical、内部リンク、重複コンテンツ。
5. **条番号の URL 表現。** 既存データの `article_num` は `"306"` や `"308_2"`
   （第308条の2）という形。URL に何を出すか、日本語の条番号との対応をどうするか。
6. **削除された条文・改正で消えた条文。** `type: "deleted"` のエントリは現在の条文が
   存在しない。ページを作るのか、作らないのか。

## 10. brief の訂正（R0 の drafts 提出後に確認。批評者・裁定者はこちらを正とする）

draft B が実データ・実 API に当たって brief の誤りを 3 件指摘し、
親セッションが全件を実測で確認した。**drafts はこの訂正の前に書かれている。**

### 10-1. §9-3 の例示が誤りだった（訂正済み）

「民法第306条は 2024 と 2026 の両方に出る」は事実に反する。306 は
`129AC0000000089_2026-03-31_2026-04-01` にしか出ない。
出荷済みデータ全体で**複数の diff にまたがる本則条文は道路交通法 `117_2_2` の1本のみ**
（2024-11-01 / 2026-04-01）。したがって §9-3 は n=1 の論点であり、ここに凝る理由は無い。

### 10-2. §7 の「未検証」を潰した — e-Gov に条文単位の取得エンドポイントは**実在する**

親セッションによる実測（2026-09-22）:

```
GET /api/2/law_data/129AC0000000089?asof=2026-09-22&elm=Article_306      → 200, 2725 bytes
GET /api/2/law_data/129AC0000000089?asof=2026-09-22&elm=Article_753:754  → 200, 1375 bytes
GET /api/2/law_data/129AC0000000089?asof=2026-09-22&elm=Article_754      → 400
    {"code":"400021","message":"要素（elm）に合致する要素が法令本文に存在しません。"}
```

**採否は設計判断として開いている。** draft B は「取得の瞬間が163個に散る／部分状態が生まれる／
`fetch_law_data` をそのまま使えなくなる」を理由に不採用としている。批評者はこの判断を攻めてよい。

なお 400 が返る事実から、**現在の民法本文に第754条という要素は存在しない**ことが確認できる
（`753:754` に畳まれている）。「削除された条文の現在の姿」は空ではなく、
「第七百五十三条及び第七百五十四条 削除」という別番号のノードである。

### 10-3. §3・§8-5 の「164ページ」は **163ページ**が正しい

ユニークな (法令, `article_num`) の組は 164。うち 1 つが範囲形 `753:754` で、
これは e-Gov の要素 ID であって条番号ではない（誰も `753:754` で検索しない）。
両 draft ともこれをページ化せず `753` と `754` に展開する方針を採っている。

**受け入れ基準 5 は「164ページ」という固定値ではなく、
「生成物から導いた条文集合と同じ枚数が静的生成されること」に読み替える。**
今日の出荷データではその枚数が 163。法令を1本足せば変わる値をテストに焼かない。
