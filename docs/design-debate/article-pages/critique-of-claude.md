# 設計案 A（design-claude.md）への批評 — R1

担当: fresh Claude #2（親セッションの文脈を持たない独立セッション）

## F1. critical — 「現在の条文」と「解説・改正履歴」の版が食い違う。12法令すべてで。しかも設計の検証器はそれを緑で通す

**指摘**: 設計は現行条文を今日 e-Gov から取得する一方、`plain_summary` / `change_description` /
`revisions` は出荷済み diff（最新でも 2026-04-01）から取る。実測すると **12法令12件すべてで、
e-Gov の最新施行版が出荷済み diff の最新日より新しい**。つまり全163ページが「知らない改正を経た本文」の
横に「その改正前に書かれた解説」と「そこで止まった改正履歴」を並べる。

**根拠**（`GET /api/2/law_revisions/<id>`、2026-09-22 実行。
`current_revision_status != "UnEnforced"` の最大 `amendment_enforcement_date`）:

```
民法          shipped 2026-04-01  egov 2026-06-24
刑法          shipped 2023-07-13  egov 2026-05-21
労働基準法     shipped 2024-05-31  egov 2026-07-17
建築基準法     shipped 2025-04-01  egov 2026-05-27
道路交通法     shipped 2026-04-01  egov 2026-07-21
著作権法       shipped 2025-06-01  egov 2026-06-24
育児介護休業法  shipped 2025-04-01  egov 2025-10-01
消費者契約法    shipped 2023-06-01  egov 2026-06-24
情プラ法       shipped 2025-04-01  egov 2026-07-17
個人情報保護法  shipped 2025-04-01  egov 2026-07-17
不動産登記法    shipped 2024-04-01  egov 2026-06-24
マイナンバー法  shipped 2024-12-02  egov 2026-07-17
```

設計 §3 の検証は「`revisions[*].date` ≤ `fetched_at` の日付」だけ。出荷データの `date_after` の
最大は 2026-04-01、`fetched_at` は 2026-09-22 なので **5か月以上の余裕で無条件に緑**。
しかも「取得後に施行された未知の改正」は `revisions` に載らないので、この検査は原理的に検出できない。
これは brief §8-4「最新施行版より古い条文が入っていない」の逆向きの穴（本文は新しく、周りが古い）で、
受け入れ基準4を満たしたことにならない。

設計案 A の §8 の自己申告（弱点1）は「静的サイトだから将来の改正は反映できない」と書いているが、
問題は将来ではなく**今日すでにズレていること**であり、自己申告はこれを覆っていない。

**処方**: 生成時に `fetch_law_revisions(law_id)`（`scripts/fetch.py:28` に実在）を呼び、
**最新施行版の `amendment_enforcement_date` を生成物に `latest_enforced` として記録**する。そのうえで
(a) `latest_enforced > max(revisions[*].date)` の条文ページは、改正履歴を「lex-diff が差分を持つ範囲」と
明示ラベルし、解説ブロック（`plain_summary`/`change_description`）を**出さない**か
「YYYY年時点の説明」と版を明記する、
(b) テストを「`latest_enforced` が生成物にあり、それが `fetched_at` 以前で、かつギャップのある条文には
解説が付いていないこと」に置き換える。
これなら赤にできる（今日の全12法令が (a) に該当するので、実装直後に赤が出る＝検算になる）。

## F2. critical — 刑法の条文ページが、廃止済みの刑名「懲役」を現行の刑として読者に出す（CLAUDE.md 事故 #3 の再現）

**指摘**: F1 の具体例。刑法の annotation は 2023-07-13 時点で書かれており、183条・241条の
`change_description` は刑を**現在形で「懲役」**と書いている。設計 A はこれを今日取得した「拘禁刑」の
条文本文の真横に置く。検証器は一切見ない（CLAUDE.md が明記する通り、刑名禁止は `law_summary.py` にだけ
スコープされており annotation には効かない）。

**根拠**:
- `frontend/public/data/140AC0000000045_2023-07-12_2023-07-13.json`、art 183 の
  `annotation.change_description`:
  「…性行為をさせた者を**3年以下の懲役**または30万円以下の罰金に処するという、既存の犯罪類型を
  定めたものです。」
- art 241 同:「刑罰の内容（**無期または7年以上の懲役**など）自体は変わっておらず…」
- 今日の e-Gov 実測（`elm=Article_183` / `Article_241`, asof=2026-09-22）:
  183「三年以下の**拘禁刑**又は三十万円以下の罰金に処する」／241「無期又は七年以上の**拘禁刑**に処する」。
  両条とも本文に「懲役」は 0 件。

**処方**: F1 の (a) に加え、条文ページで使う annotation 由来の散文に対して
`validate_summary_shape` と同種の廃止刑名チェックを**新規に**かける
（`law_summary.py` のスコープ外なので流用ではなく追加が要る）。
少なくとも「本文に拘禁刑があり解説に懲役がある」条文を生成時に raise。

## F3. critical — `cross_references` はページ内リンクに使える形をしていない

**指摘**: 設計 §2.2 の `has_page`（「cross_reference の指す条文がこの法令のページ集合に居るか」）は、
`cross_references[].article_num` が正規の `article_num` 形式であることを前提にしている。
実データはそうなっていない。LLM 生成の自由記述で、**他法令への参照 34 件**、**空文字 10 件**、
`article_num` の表記ゆれ（`_` / `-` / `の`）が混在する。素直に実装すると
「民法第八百十七条の二第一項」というラベルが**育児介護休業法**の `/article/817-2` を指す、
「附則第三条」が**本則第三条**を指す、といった誤リンクになる。

**根拠**（出荷データ全665件を集計）:
```
形式:  plain 556 / underscore 128 / hyphen 50 / other 16 / EMPTY 10
他法令を指す ref: 34 件
例: 建築基準法 art6   → ref "景観法第七十四条第一項", article_num "74"
    建築基準法 art68_9 → ref "景観法第七十四条第一項", article_num ""
    育児介護休業法 art2 → ref "民法第八百十七条の二第一項", article_num "817-2"
    マイナンバー法 art132 → ref "…番号法第二条第九項", article_num "2"
other の実例: "16の2" / "21の2" / "附則3" / "817の12" / "778の4"
hyphen の実例: "18-2" / "38-8" / "548-2"
```
設計 §4 が定める slug（`_`→`-`）と、cross_reference が実際に持っている値は**別の生成系**であり、
一致は保証されていない。

**処方**: `has_page` の判定を `article_num` ではなく **`ref` 文字列**でやる。
(1) `ref` が `第…条` で始まらない（＝法令名が前置されている）ものは無条件で `has_page=false`、
(2) `ref` に「附則」を含むものも false、
(3) 残りは `ref` の漢数字条番号を正規化して同法令の slug 集合と突き合わせる。
そして**マッチしなかった件数を生成時に出力し、テストで上限を固定する**。
`article_num` フィールドは信用しない。

## F4. high — `caption` は既存の関数から取れない

**指摘**: 設計 §2.2 の例は `heading: "第三百六条"` と `caption: "（一般の先取特権）"` を別キーで持ち、
§5 の `generateMetadata` は `民法 第306条（一般の先取特権）｜…` というタイトルを作る。しかし
(a) 出荷済み diff の `title_after` には caption が **165件中0件**、
(b) 設計が「そのまま使う」と宣言した `find_articles` は、e-Gov の実際の木では caption を**取りこぼす**。

**根拠**:
- 出荷データ全 本則165件で `title_before`/`title_after` に空白も `（` も含むものは 0 件。
- e-Gov 実測（`Article_306`）の children 順は `ArticleCaption` → `ArticleTitle` → `Paragraph`。
  `scripts/diff.py:143-152` は `ArticleCaption` で `title = f"{title} {caption}"` した後、
  `ArticleTitle` で `title = extract_text(child).strip()` と**上書き**する。
  実行確認: `find_articles` の出力は `title == '第三百六条'`（caption は消える）。
- `article_to_lines`（`scripts/diff.py:222`）は title を `lines[0]` に入れる単一文字列なので、
  設計が言う「`current_lines` は `article_to_lines` の出力形」と「`heading`/`caption` を別キーで持つ」は
  両立しない。

SEO 上も痛い。brief §1 で唯一見えている実クエリが「民法 第754条 **夫婦間の契約の取消権**」＝ caption 語で
あり、タイトルに入れたい語がまさに取れていない値。

**処方**: `find_articles` の caption 上書きは**既存のバグ**として別 PR で直す。
条文ページ側は `caption` を独立キーで受け取り、**caption が取れなかった条文では `<title>` から
括弧ごと落とす**（空括弧 `第306条（）` を出さない）。テストに「全ページの title に空の括弧が無い」を足す。

## high — 設計 A は brief §10 の訂正前に書かれており、2点が訂正と矛盾する

- §5「`generateStaticParams()` → 164 件」／§7「`npm run build` が **164ページ**を静的生成することを
  確認する」。brief §10-3 は **163** が正しいと訂正し、さらに「固定値をテストに焼かない」と指示している。
- §0-2・§1 は e-Gov の条文単位取得（`elm=`）に一切触れていない。brief §10-2 はこれを
  「実在する／採否は設計判断として開いている」と明記している。
  **設計 A は選択肢を検討した形跡がないまま法令全文取得を採っている**ので、これは意識的な判断ではなく未認識。

**処方**: 受け入れ基準を「`articles/*.json` から導いた slug の総数 == 生成ページ数」に書き換える。
`elm=` については採否の理由を1行で書く。

## high — 「Python と TS の slug が一致することをテストで固定する」が、TS 側を一度も実行しない

**指摘**: 設計 §4 の突き合わせは、出荷データの `slug` を書いたのが Python 側なので
**Python を Python 自身と比べているだけ**。TS 側は緑のまま自由にズレられる。
`307_2` を TS だけが `307_2` のまま出せば 404 リンクが生まれ、テストは緑。

**処方**: TS 側の `articleSlug()` を捨てて、cross_reference の解決も**生成時に Python でやって
`slug`/`has_page` を焼き込む**。

## medium — `753:754` の展開ロジックは、実データでは常に畳まれて消える

**指摘**: §2.3 は「範囲エントリを 753 と 754 に展開し `change_description` を両方に載せる」→
「(date, diff_id) が重複するので個別側を優先して畳む」と書く。実データでは範囲エントリは1件だけで、
その `diff_id`・`date` は 753・754 の個別 `deleted` エントリと**完全に同一**。
つまり展開したものは 100% 畳まれて消える。

しかも畳まれるのは良いことでもある: 範囲エントリの `plain_summary` は
「夫婦の間で結んだ契約を婚姻中はいつでも取り消せるとする…」＝ **754 の話しか書いていない**ので、
753 のページに載せたら誤りになる。`type` も `"added"`（削除の記述なのに）。

**処方**: 展開＋畳み込みではなく「範囲形 `article_num` は **個別エントリが存在するなら捨てる**、
存在しないなら raise」にする。テストは `test_range_article_expands_to_members` ではなく
`test_range_entry_without_individual_raises` にする。今のテスト名は、実際には起きない振る舞いを緑にする。

## medium — 削除条文ページの本文が、廃止された条文テキストそのものになる

**指摘**: §2.2 の 754 の例は `current_lines: []`、`former_lines` に廃止された条文。
§5 の描画は `article-text.tsx` 1つが両方を描く、としか書かれていない。結果、/article/754 のページ本文に
表示される唯一の条文テキストが**廃止済みの条文**になる。検証器は見ない領域（手書きテンプレート文言）。

実測では今日の民法に `Article Num="753:754"`（「第七百五十三条及び第七百五十四条 削除」）が実在する
（`elm=Article_753` と `Article_754` は 400、`Article_753:754` は 200）。「現在の姿は空」ではない。

**処方**: `former_lines` を描くブロックは**別コンポーネント**にし、見出しに
「2026年4月1日に削除された当時の条文（現行法ではありません）」を**テンプレート文言として固定**する。
削除ページでは現在の姿（`753:754` ノードの「削除」表記）を先に出す。

## medium — `/article` → `/diff#<article_num>` のアンカーが存在しない。§5 と §6 が矛盾

**根拠**: `grep -n "id=" frontend/components/diff-viewer.tsx` → ヒット 0（`key=` のみ）。
§6 は「`/diff` のページ構成は変えない」と書き、§5 は「`/diff` の各条文見出しからリンクする」と書く。
リンク追加は構成変更。

**処方**: §6 の禁止文を「レイアウト・本文は変えない、アンカーとリンクのみ足す」に書き直す。

## medium — 生成の運用（誰が・いつ回すか）が空白のまま、鮮度が出荷物の中心的な主張になっている

§8-1 が自認しているが、brief §8-4 は鮮度を出荷条件にしているので、これは弱点の申告ではなく
**受け入れ基準の未達**。F1 と組み合わさると、`fetched_at` は書かれるが誰も見ず、CI は永遠に緑、
ページは静かに腐る。

**処方**: 「全 `articles/*.json` の `fetched_at` が今日から N 日以内」で**期限切れで CI を赤にする**。
今の設計の検査（`revisions[*].date <= fetched_at`）は逆に、何年前のファイルでも緑にする。

## low — `lawtext.py` への関数移動は本機能に不要

設計自身が §8-2 で認めている。加えて F4 の通り `find_articles` には caption 取りこぼしの実バグがあるので、
**移動 PR と修正 PR が混ざると「振る舞いは変えない」という受け入れ条件が成立しなくなる**。

**処方**: 順序は ①caption バグ修正（既存テストで赤→緑）→ ②移動（振る舞い不変）→ ③条文ページ。

## この設計の最も弱い一点

**「鮮度」を条文本文だけの問題として解き、その隣に置く解説と改正履歴の鮮度を検査していないこと。**

brief §6-1 の根っこは「ディスク上のファイルは *いつ取得したか* を記録していない」で、設計 A は
それに `fetched_at` で答えた。答えとしては正しい。だが条文ページは「今日の本文」と「2023年の解説」を
**1枚に並べる**部品であり、そこで初めて成立する失敗——本文と散文の版ズレ——を設計はどこでも
検査していない。実測では12法令12件すべてがすでにズレており、刑法183条・241条では「拘禁刑」の本文の横に
「懲役」の解説が出る。CLAUDE.md が事故として記録している当のものが、新しいページ型で、
しかも検証器の効かない場所に再現する。

設計 §3 の検査（`revisions[*].date <= fetched_at`）はこのズレを**定義上検出できない**。
ズレの原因は「知らない改正」であり、知らない改正は `revisions` に載らないからだ。
緑になるが守っていないテストの教科書的な形。
