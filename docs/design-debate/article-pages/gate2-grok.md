設計文書の残りと、計画が前提にしている実コードを突き合わせて検証します。まず計画の末尾と、再利用すると書いてある関数の実シグネチャを見ます。再利用する関数の実体と、出荷データの形が計画の前提と合うかを確認します。出荷済みの diff と手元の法令 XML に、計画の解決順と相互参照の判定を当てて、実際に壊れるかを数えます。致命的な穴、つまり出荷不能やデータの破壊に相当するものは、この計画には無い。取得に失敗したら何も書かない、範囲エントリを勝手に展開しない、解説本文は版が揃ったときだけ現行欄に出す、という骨格は仕様と手元のデータに合っている。

壊れているのはその周りの「現行として見せる」境界である。解説文だけゲートを通し、関連条文・並び・戻りリンク・出荷検査が仕様の外に残っている。以下はリポジトリの出荷 diff と 2026-09-08〜09 の生データに計画のコードを当てて確認した。

## 重要

**版が違っても、関連条文を現行のリンクとして出す。** 仕様 §4 は、本文が一致しないとき cross reference を「関連する条文」にせず、同じ履歴カードへ時点付きで移すと決めている。Task 6 は `matched` を `current_summary` にしか使わず、最新 annotation の参照を常に `related_articles` に入れる。`changes` にも参照フィールドが無いので、履歴カード側に移す実装ができない。

2026-09-08 時点の本文と突き合わせると、対象 163 条のうち本文不一致は 32 条、そのうち参照を持つのは 29 条、参照行は 144 件。著作権法 122 条の 2 は、現行本文が帳簿の罰金なのに解説は秘密保持命令のまま、という仕様が挙げる事故そのものだが、この条の `cross_references` は空なので偶然助かる。刑法 181 条のように参照が残っている不一致ページは、古い条へのリンクが「関連する条文」として出る。方向は、一致したときだけ `related_articles` を埋め、不一致の参照は `changes[]` に日付と一緒に載せること。

**条の別名は、最初に見つかった短い方で切れる。** `resolve_cross_references` は別名表を挿入順に見て、`startswith` の最初のヒットで決める。民法では「第七百七十八条」が「第七百七十八条の四」より先に一致する。短い方の番号と `article_num` が食い違うので veto が掛かり、リンクは出ない。出荷データではこの形が 51 件あり、最長一致にすれば 48 件は正しい条へリンクできる。誤リンクの出荷は、今の 663 件では 0 件だった。空の `article_num` や、短い番号が入った参照が 1 件入ると、そのまま短い条へリンクする。Task 5 のテストの別名表には「第三百八条の二」しか無く、「第三百八条」が同居しないので、この分岐は緑のまま通る。別名は長い順に試し、一致した末尾がさらに「の」や数字で続かないこと。

**法令ページの条文順が辞書順になる。** `build_law_articles` は slug の文字列順で並べ、Task 10 の一覧はその順を使う。刑法は第176条の次に第3条、道路交通法は第125条の次に第2条、になる。対象のある 11 法令のうち 9 法令で、数値順と一致しない。ここが条文ページへの唯一のクロール経路なので、並びがそのまま目次になる。`article_num` を `_` で割って数値の列として比べる。

**出荷検査は、名前と違い本文一致を見ていない。** 保存する `changes` から `paragraphs_after` が落ちている。`test_a_shipped_summary_means_the_text_still_matched` が断言しているのは廃止刑名の部分文字列だけで、著作権法 122 条の 2 のように刑名を含まない別条文の解説は、`current_summary` に入れてもこのテストは通る。仕様 §10 が求める「`current_summary` があるページは本文一致ゲートを通っている」は、出荷 diff の最新 `paragraphs_after` と JSON の現行本文で `texts_match` をやり直さないと検査にならない。

**Task 7 は、書いたテストを通せない。** `main()` は取得失敗を `httpx.HTTPError`、本文欠落を `ValueError` のまま投げる。テストはどちらも `SystemExit` を期待している。日付のテストは 2 回目の `now()` で日付を進めるが、2 回目は `fetched_at` の生成に使われ、`validate_articles` が「asof と fetched_at が別の日」で先に `sys.exit(2)` する。終了コード 3 には届かない。日をまたいだときも、取得より前に日付が変わると「検証失敗」になり、仕様が分けた「日付が変わった」と区別が付かない。番兵の比較を `fetched_at` の検査より前に置くか、`fetched_at` は開始時の `today` から組み立て、テストの時計は全法令の `fetched_at` を打った後で進める。

**削除条文の見出しが、753 条で逆の意味になる。** 仕様の見出しは「今回の改正直前の条文」。計画の `FormerArticleText` は「削除される前の条文」。民法 753 条の `paragraphs_before` はすでに「削除」という 1 行で、この改正が消したのは欠番表示そのものである。見出しどおり読むと、成年擬制の本文がそこにあるように見える。表示順も仕様 §8 と違い、この旧本文が「未収録です」より前に出る。見出しを仕様の文言にし、現行の説明を旧本文より前に置く。

**`/diff` への導線が、仕様の戻りリンクになっていない。** 履歴カードのリンクは `/diff/${diff_id}` だけで、`#条番号` が無い。Self-Review は diff 側に `id` を付ければ足りると書いているが、戻る側がハッシュを付けないとその `id` は使われない。加えて、既存の見出しは展開用の `<button>` なので、その中に `Link` を置くとボタンの中のリンクになり、クリックが展開と遷移の両方に掛かる。`id` はカードの外側の要素に付け、リンクはボタンの外に置く。

もう一つ、労働基準法は本則 0 件で JSON を作らない。`getArticleData` はファイルが無いと `readFileSync` で落ちる。diff ページが無条件にこれを呼ぶと、附則だけの diff 2 本で `npm run build` が止まる。`getArticleLawIds()` に無い法令は空の対応表を渡す。

**未収録の案内が、ダークモードで背景に溶ける。** サイトは `prefers-color-scheme: dark` で背景 `#0d1117`、文字色は CSS 変数に乗っている。新しいコンポーネントは `text-gray-600`、`border-gray-200`、`bg-amber-50` を直接塗っている。版不一致のページで一番読んでほしい「現行本文に対応する解説は未収録です」が、暗い背景の上の灰色になる。既存の diff カードと同じ変数（`--foreground`、`--muted`、`--border`）に乗せる。

**description が、載っていないものを載せたと言う。** 仕様 §9 は、取得日時点の条文と収録済み改正年までに限定している。計画の文面は「改正前後の条文、関連する条文へのリンクを掲載」である。`former` は削除条文にしか無く、変更されただけの条では改正前の本文はページに無い。不一致ページでは関連リンクも、上の修正を入れると現行欄から消える。取得日と改正年だけにする。

## 軽微

- 検証コマンドの `-k collect or range or ...` がクォートされていない。シェルの `or` として切れ、失敗確認の pytest が意図した絞り込みにならない。Task 2 以降の同じ形も同じ。
- `new Date("2026-09-22")` は UTC 正午ではなく UTC 午前 0 時として読まれる。GitHub Actions は UTC なので今の CI では日付はずれない。アメリカ時間で `npm run build` すると「時点」が 1 日前になる。日付文字列を分解して組む。
- 対象 0 件になった法令の古い `articles/<lawId>.json` を消さない。再実行で「ファイルを作らない」が、前回のファイルが残る。公開前に今回の成果物へディレクトリごと置き換えると、仕様 §3 の一括置換にも寄る。
- 一覧のグループは `section_path[0]` だけなので、民法は親族編 36 本が一段になる。章で分けるなら `[1]` を見る。
- `extract_text` はルビの読みも連結する。実データに「失踪そうの宣告」がある。いまの 163 条の caption にルビは無かった。対象を広げると `<title>` に読みが混ざる。caption では `Rt` を落とす。

## 確認したいこと

仕様が「育児介護休業法の 36:52 は 17 条ぶんの実体」と書いている件は、手元の `403AC0000000076_2026-09-08.json` では本文が「削除」だけで、36 から 52 の個別ノードは無い。計画の「本文が削除のときだけ欠番として解決する」は、このスナップショットでは正しい方向に倒れる。引用されている実測と、ディスク上の法令が食い違っている。今日の API では取り直していない。
