計画の残りと、根拠にしている API・データ形状をリポジトリで突き合わせます。前提がコードと食い違うところから潰します。計画が前提にしている関数の引数と、出荷データの実形状を突き合わせます。ここが崩れると生成全体が止まります。要は、この計画でページ生成は通る。前回塞いだ「今の欄に過去の出所を入れる」本筋は、法令名・解説・関連リンクについては閉じている。残るのは、条文として読めるかを落とす穴が2つと、仕様が撤回した偽の例をテストが根拠として呼び戻していること。

## 重要

### 1. 第2項以降の項番号が、データにも画面にも残らない

民法772条の現行XMLでは、第1項の `ParagraphNum` は空、第2項の `ParagraphNum` は「２」である。属性 `Num` は `"1"` `"2"` `"3"` `"4"`。出荷 diff の `paragraphs_after` もこの番号を持っている。複数項の改正エントリは107件ある。

`format_paragraph` は `ParagraphNum` を読み飛ばす。計画の `extract_article_body` はそのテキストだけを受け、番号は属性を読まず `1, 2, 3…` と振り直す。画面は `p.text` しか描かない。772条は次の4塊になる。

- 第1項（中に文が2つある）
- 「前項の場合において、婚姻の成立の日から二百日以内に…」
- 「第一項の場合において…」
- 「前三項の規定により…」

「前項」「第一項」は本文に残るので、塊を数えれば項は追える。公式の条文が欄外に置く「２」「３」「４」はページに無い。引用する読者は、第1項の2文を2つの項と数え間違える。

仕様§4は比較対象を「段落番号と本文」としている。`texts_match` は本文の一致と個数だけを見る。今の出荷分は番号がすべて `1..n` なので、ゲートの合否は本文比較だけで決まっていて、この穴はテストに出ない。テストの `_article` も `ParagraphNum` を置いていない。

方向: `find_articles` と同じく `Paragraph@Num` を読む。画面には、空でない `ParagraphNum`（第2項なら「２」）を項の頭に出す。`texts_match` はその番号も比べる。連番の作り直しは、属性が空の単項と公式の「２」を同じものに見せてしまう。

### 2. 削除条文の章が、今日の木にあるのに空になる

民法753・754の個別ノードは今日の本文に無い。あるのは `Num="753:754"` で、段落本文は「削除」。このノードは「第四編 親族 / 第二章 婚姻 / 第二節 婚姻の効力」の中にある。出荷 diff の753も同じ `section_path` を持っている。

`build_law_articles` は `find_section_path(law_full_text, num)` を個別番号 `"753"` で呼ぶ。その番号の `Article` は無いので `None` になり、`section_path` は `[]`。ページの編章行は消え、法令ページの「改正された条文」では見出しのないグループに落ちる。欠番の2ページだけが、親族編から外れて並ぶ。

仕様の出所表が求めるのは「今日の木から編章を取る」ことである。今日の木でその条を代表しているキーは `current["source_article_num"]`（`"753:754"`）の方である。

方向: `merged_deleted` のときは範囲ノードの番号で `find_section_path` を呼ぶ。個別番号で見つからないときに diff の古い `section_path` へ戻すと、出所表が禁じた過去データが復活する。

### 3. 撤回した「36:52は実体がある」が、テストのコメントとして戻っている

仕様§6の訂正は、育児介護休業法の `36:52` が17条分の実体を覆う、という説明が偽だと書いている。2026-09-08 の本文は「第三十六条から第五十二条まで」＋段落「削除」だけである。個別の第40条は無い。

Task 3 のテストは、その偽の文を根拠のまま残している。

```python
# 育児介護休業法 ships a real 36:52 node covering 17 articles.
```

フィクスチャの本文は「実体のある本文」で、テストが固定している挙動（本文が「削除」でなければ吸収しない）自体は正しい。壊れているのは根拠である。同じタスクの実装コメントは「36:52 を例にするな」と直してある。テストと実装で、この範囲ノードの事実が逆になる。

この規則を次に触る人はテストのコメントを実測として読む。仕様が訂正を残した理由は、その読みで規則を「直す」ことだった。

方向: コメントから法令名と「実在する」を削る。「本文が削除でない範囲には入れない」という合成フィクスチャだと書く。

## 軽微

- **アンダースコアを省いた条番号を、別条として落としている。** ラベルは正しく解決したうえで `article_num` が食い違うとリンクしない、という veto は仕様どおりである。ただし正規化は `-` と `の` だけで、`7782`・`7784`・`81713` はそのまま残る。出荷データでこの veto に落ちるのは8件で、いずれも日本語ラベルは目的の条（`778_2` や `817_13`）を指している。`824` と `824_2` のように親番号だけが入っているものは、落とすのが仕様の意図に合う。`7782` は表記が欠けているだけで、別の条ではない。誤リンクにはならない。関連リンクが黙って8件消える。
- **`label` が空のとき `title_before` に落ちる。** `build_law_articles` の `current["source_label"] or title_before` は、出所表が「漢数字の条名は今日の `ArticleTitle`」と閉じたあとに残った口である。今の対象条文では `ArticleTitle` は空でないので、今日の生成では発火しない。空になった回に、別名表へ過去の見出しが入る。
- **公開はファイルごとの `os.replace` である。** 検証に落ちたとき、日付が変わったときに1件も書かない、という経路はテストがある。11法令を書いた途中でプロセスが死ぬと、先に書いた法令だけ新しい JSON になる。仕様§3の「一時ファイルからまとめて置き換える」には、成功分を一時ディレクトリに書いてからディレクトリごと入れ替える方が近い。
- **出荷検査に「削除ページは `merged_deleted` かつ `former`」が無い。** `validate_articles` は、状態が `merged_deleted` なら `former` があることを見る。削除条文を `present` のまま出しても、出荷テストは通る。単体テストは合成木でこの分岐を見ている。実データの753・754を出荷 JSON 側で固定していない。

## 確認したいこと

仕様§4の履歴カードは「改正直後の条文についての説明」と固定している。計画は `type === "deleted"` のとき「改正直前」にする。民法754の `paragraphs_after` は空で、改正直後の本文は範囲ノードの「削除」なので、直後と書くと解説が削除という文字の説明になる。分岐の方が事実に合う。仕様の文は直っていない。実装中に仕様へ合わせて「直後」へ戻すと、この2ページだけ説明の時点が逆になる。仕様側の文を先に直すのか、計画の分岐を正とするのか。
