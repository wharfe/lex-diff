# #23 出荷済み diff を最新施行版まで追いつかせる — 仕様（1ページ）

## 要は何

12 法令について、出荷済みの最新版から今日（2026-10-09, JST）までに施行された改正を
**(法令, 施行日) の重複なしで全 60 組**、1 組 = 1 diff で作る（ユーザー確定: 範囲は全件）。
同じ日に複数の改正法が施行される組が新規 7・出荷済み 3（刑法 2025-06-01 の拘禁刑一本化を含む）。
表が変わった 13 組は保留（#28）。残りに条・附則の変更 0 件の組は無い。

## Gate 2 第2周で spec に戻った理由

「同じ日の改正を 1 本の法律の手柄にする」が 2 周続けて別の経路から出た（第1周: annotate、
第2周: explainer と提出者）。制約は手段由来だった — 「各部品が自分の情報源で改正名を付ける」。
手段を替える: **diff が自分の改正名を持つ唯一の場所**で、改正名を出す部品は diff から読む。
複数の法令を含む diff では、どの部品も変更を 1 本に帰属させず、diff に提出者を付けない。

## 不変条件（壊したら失敗）

1. **年表に後から足した情報を消さない。** `timeline.py` は作り直すたびに `summary`
   `category` `contributors` `explainer` と各 entry の `proposer` を落としていた。出荷中の
   年表から引き継ぐ（`carry_over`）。entry の対応は `law_revision_id` で取る。
2. **年表は出荷されている diff にだけリンクする。** `diff_id` は `frontend/public/data/`
   に実在するファイルで決める（以前は `data/diffs/` を見ていたため、annotate が出荷を
   拒んだ diff にも 404 リンクが出えた）。テスト: `test_every_timeline_link_points_at_a_shipped_diff`。
3. **同じ日の改正を 1 本の法律の手柄にしない。** `diff.py` はその日に施行される改正法を
   すべて `revision_after.amendment_law_title`（「／」区切り、全表示箇所がこの 1 欄を読む）
   と `amendment_law_titles` に書く。pr_summary のプロンプトは、複数のときだけ
   「どの変更がどの法令によるものかは分からない、帰属させるな」と書き足す。単独のときは
   文面が 1 バイトも変わらない（条文ごとの注釈は法令名を使わないので、その cache は有効のまま。
   `PROMPT_VERSION` は条文注釈の cache 用なので上げない）。
4. **diff の提出者は年表の entry から写す（複数法令の diff には付けない）。** 施行年で NDL を検索し直すと、毎年出る題名
   （道路交通法の一部を改正する法律など）で別の年の大臣が付く。`revision_after.law_revision_id`
   で年表の entry を引き、その `proposer`（公布年で検索したもの）を写す。
   テスト: `test_a_diffs_proposer_is_its_timeline_entrys`（今の出荷データでは赤＝16 本とも未設定）。
5. **捏造防止の形は変えない。** 検証器と版整合ゲートはいじらない。
6. 条・附則の変更 0 件の組は diff を書かず、前回の同名ファイルも消す（年表ではリンクなし）。
7. **表が変わった組は出さない（#28）。** `diff.py` は条文中の表を `[表]` に潰し、別表を読まない
   ので、表の変更が見えない。`tables_changed`（表の中身だけで比較、属性は無視）が真なら
   diff を書かず終了コード 3。出荷側のファイルには触れない（公開中の 2 本は据え置き＝ユーザー判断）。
8. **explainer は diff の改正名で書く。** `apply_diff` が grounded な変更の題名を diff の
   `amendment_law_title` に替え、複数法令なら帰属させない旨をプロンプトに足す。

## Gate 2 第3周の後（周回上限）

第2周で足した「別表が変わった」印と注意書きは、第3周で high 4 件のうち 3 件を生んだ
（属性だけの差で誤検出、「附則だけ」の文面と矛盾、画面が「変更は附則のみ」と表示）。
同じ根（表が差分に見えない）から 2 周続けて出たので、ユーザーに上げて手段を替えた:
**表が変わった組は今回出さない**（新規 11 組を保留、公開中の 2 本は据え置き。#28）。
残りの 1 件（再注釈に失敗した同じ日の diff が単独の題名のまま緑で出荷される）は
`test_a_diff_names_every_law_enforced_that_day`（年表と照合）で塞いだ。

## やらないこと

- 定期再生成の自動化（別 issue）。施行日が未来の改正。
- 同じ日の改正の変更を、改正法ごとに振り分けること（本則には由来の印が無い）。
- 範囲条文で `articles.py` が落ちた場合の分割（落ちたら止めて報告し、別 issue）。

## 実行順

1. 全 76 組（新規 60 + 既存 16）で、新しい `diff.py` をかけ直す（済: 63 本が書かれ、
   表で保留 13、`amendment_law_titles` を持つ diff 7 本）
2. 新しい diff 49 本と、法令名が変わった既存 diff 2 本に `annotate.py`。
   失敗した組は出荷しない。diff を最後に書くのは手順 4 の enrich
3. 法令ごとに `timeline.py`
4. `enrich.py`（年表の entry → diff の順）
5. 法令ごとに `law_summary.py` → `explainer.py` の順で 1 本ずつ（同じ年表ファイルを読み書きし、
   explainer は summary を読む）。片方が落ちても他方は走らせる。作り直せなかった法令を報告に挙げる
   （その法令では引き継いだ古い文章が残る）
6. `articles.py --all`
7. まとめて 1 コミット（`test_shipped_data.py` は diff・年表・条文ページの整合を見るので、
   途中の段階でコミットすると赤になる）
